# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Taliesin: a collaborative, browser-based live-coding music sequencer. SvelteKit (static adapter) + Svelte 5 runes + Tailwind 4 + Skeleton UI. Audio is generated by [Strudel](https://strudel.cc) pattern code; multiple clients sync over WebRTC via Trystero (Nostr signalling). Package manager is yarn.

## Commands

- `yarn dev` — dev server (uses `vite-plugin-mkcert`, so it serves HTTPS)
- `yarn build` / `yarn preview`
- `yarn check` — svelte-check / typecheck
- `yarn lint` (prettier --check + eslint); `yarn format` to fix formatting
- `yarn test` — vitest once (`yarn test:unit` for watch). Single file: `yarn test:unit --run src/lib/Store.svelte.test.ts`; single test: add `-t "name"`.
- `yarn storybook` (port 6006)

Vitest has three workspaces: `client` (jsdom, `*.svelte.{test,spec}.ts`), `server` (node, other tests), and `storybook` (Playwright browser). `VITEST` is true in tests, which makes `strudel.ts` and `Store.svelte.ts` swap in stubs (no audio, no network room) — keep that guard when touching those modules.

`nostr-relay/` is an optional local Go Nostr relay for signalling (see the commented `relayUrls` in `src/lib/Store.svelte.ts`).

## Testing

- `yarn test` runs unit + component tests on an in-memory network (`src/lib/testing/fakeRoom.ts`: per-peer latency, queued and randomised delivery, per-link FIFO) with a recording `fakePlayer`.
- `yarn test:e2e` runs two real Chromium pages over real WebRTC through a local Node Nostr relay (`e2e/`); it spawns its own dev server (`E2E=1` serves plain http). The app exposes `window.__store` with `?debug`, and `?relay=ws://…` overrides signalling.
- `yarn run check` is clean (0 errors); keep it that way. Use `yarn run check`, because bare `yarn check` is a yarn built-in.

## Architecture

**Data model (`src/lib/instruments.ts`, `parts.svelte.ts`)**: An `Instrument` (class, in `src/lib/instruments/` e.g. `Drum`, `MonoSynth`) is a stateless behaviour object; its state lives in a plain JSON-serializable `InstrumentData` containing a list of `InstrumentPartData` (identified by `partName`, which is the part class's `.name`). Each *part* (`InstrumentPart` subclass: Effects, Filter, Steps, Chords, Arpeggiator, MonoSequence, Octave, TrackNotes) defines `createData`, `assign`, and `generate(...)` which emits a fragment of Strudel code. Look parts up with `getPart(PartClass, data)`. Because class `.name` is the key, esbuild is configured with `keepNames` / no identifier minification — don't rename part classes casually, it breaks serialized state.

**Code generation**: `Instrument.generate(data)` concatenates part outputs in a fixed order (input part → chords → arpeggiator → `.fast(steps)` → filter → effects → instrument-specific → gain). The whole song is a string of Strudel code evaluated by `strudel.evaluate` (`src/lib/strudel.ts`, a singleton `StrudelWrapper` around `@strudel/web`; it also polls scheduler time every 250ms into the `time` store for playhead display).

**Commands (`src/lib/commands.ts`)**: views never mutate song state. They `dispatch` a `Command` (`setCells`, `setPartFields`, `setInstrumentFields`, `addInstrument`, `removeInstrument`, `setMasterVolume`, `transport`). Commands are JSON, *absolute* (never toggle/increment), addressed by instrument `id` (never index), and anything non-deterministic (random notes, new ids) is resolved before dispatch (`lib/commandBuilders.ts`). `applySongCommand` validates and applies them in place; it also runs on network input, so it must reject anything malformed. `store.dispatch` is the single entry point: it applies locally, appends to `store.commandLog` (replayable), and sends to the host. **The host is the single sequencer**: it applies client commands and rebroadcasts them in arrival order (`ordered: true`); clients only accept the host's ordered stream. That is what makes concurrent edits converge (see the randomised convergence test). Views get `dispatch` (and state) as props, so they can be tested with a spy. `lib/gesture.ts` holds the sequencer's drag rules as pure functions. Part views stay `bind:`-based against a local draft in `InstrumentPartView`, which diffs it into `setPartFields`.

**Store & networking (`src/lib/Store.svelte.ts`)**: `AppStore` (global `store`, created via `initStore(host, roomId)`; tests construct it directly with an injected room and player) holds the song as Svelte `$state`, the registries (`parts`, `partMap`, `presets`, instrument map), and Trystero actions: `'state'` (full instrument list: the host sends it when a peer connects), `'cmd'` (commands), plus `'transport'`/`'transportReq'` (`lib/transport.svelte.ts`: host-authoritative play/stop; clients mirror it, send requests, and extrapolate the playhead; sequence numbers drop stale messages). Every peer runs Strudel and plays the song itself: the host owns the transport, and clients start their scheduler at the host's position (`Transport.reconcile`: ping-compensated, output-latency-compensated, drift corrected by `shift` beyond 40 ms). Clients need a user gesture to unlock audio (`strudel.audioRunning`, the "Tap to hear" button). Compare peers' `scheduler.now()`, not wall-clock guesses; e2e measures the skew. `mixerIndex = -1` addresses the mixer as a pseudo-instrument. `instruments.ts` and `Store.svelte.ts` import each other (circular), so import `Instrument` from `$lib/instruments`, never from the `$lib` index, inside `lib/instruments/*`.

**UI**: `src/routes/+page.svelte` sets the global context (`lib/context.ts`: host/roomId/scale) and renders the instruments. `components/InstrumentView` → `InstrumentPartView` dispatch to `Part*View` components per part; `src/instruments/` holds instrument-specific views (`SequencerView` grid, `PianoScaleView`). Touch gestures use hammerjs via `lib/utils/hammerAction.ts`. `lib/sequencer.ts` adapts a part (steps/notes) to the grid `ISequencer` interface.

**Start page & saving**: `/home` starts a jam (`lib/room.ts`: short room codes, `parseRoom` accepts a pasted share link or code). The host autosaves the song to `localStorage` per room (`taliesin:song:<room>`, debounced, restored through the command reducer so bad data is dropped); clients never save.

**Acoustic calibration (`src/lib/calibration/`)**: the browser's reported output latency is often wrong (Bluetooth), so devices in the same room can be measured. The host's "Calibrate" button records its microphone while each guest plays a probe chirp on request; the host times the arrival against its own speaker-to-mic delay (same input path, so mic latency cancels) and sends the guest `round`; the guest subtracts the network delay it assumes and applies the result as `transport.offset`, which *replaces* the reported-latency term in `Transport.target()`. `dsp.ts` is pure (chirps, FFT, normalised cross-correlation: raw correlation peaks accept any loud beep, so keep it normalised); `calibration.svelte.ts` is the protocol over an injected `Acoustics`; `webAcoustics.ts` is the real Web Audio/AudioWorklet implementation. Unit tests simulate the air; e2e loops the real audio graph back into the worklet. Only meaningful for co-located devices, with the song stopped.

**TURN relay (`src/lib/turn.ts`, `worker/`)**: peers on mobile data or strict NATs need a TURN relay. `routes/+page.ts` fetches short-lived ICE servers from `VITE_TURN_ENDPOINT` (or `?turn=<url>`) before the room is joined; failure just means no relay. `worker/turn.ts` is the Cloudflare Worker that holds the API token (setup in `worker/README.md`). Static `VITE_TURN_URLS/USERNAME/CREDENTIAL` also work for providers with fixed credentials.
