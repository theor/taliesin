# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Taliesin: a collaborative, browser-based live-coding music sequencer. SvelteKit (static adapter) + Svelte 5 runes + Tailwind 4 + Skeleton UI. Audio is generated by [Strudel](https://strudel.cc) pattern code; multiple clients sync over WebRTC via Trystero (Nostr signalling). Package manager is yarn.

## Commands

- `yarn dev` — dev server (uses `vite-plugin-mkcert`, so it serves HTTPS)
- `yarn build` / `yarn preview`
- `yarn check` — svelte-check / typecheck
- `yarn lint` (prettier --check + eslint); `yarn format` to fix formatting
- `yarn test` — vitest once (`yarn test:unit` for watch). Single file: `yarn test:unit --run src/lib/Store.svelte.test.ts`; single test: add `-t "name"`.
- `yarn storybook` (port 6006)

Vitest has three workspaces: `client` (jsdom, `*.svelte.{test,spec}.ts`), `server` (node, other tests), and `storybook` (Playwright browser). `VITEST` is true in tests, which makes `strudel.ts` and `Store.svelte.ts` swap in stubs (no audio, no network room) — keep that guard when touching those modules.

`nostr-relay/` is an optional local Go Nostr relay for signalling (see the commented `relayUrls` in `src/lib/Store.svelte.ts`).

## Testing

- `yarn test` runs unit + component tests on an in-memory network (`src/lib/testing/fakeRoom.ts`: per-peer latency, queued and randomised delivery, per-link FIFO) with a recording `fakePlayer`.
- `yarn test:e2e` (set `E2E_APP_PORT` if 5199 is busy) runs two real Chromium pages over real WebRTC through a local Node Nostr relay (`e2e/`); it spawns its own dev server (`E2E=1` serves plain http). The app exposes `window.__store` with `?debug`, and `?relay=ws://…` overrides signalling.
- `yarn run check` is clean (0 errors); keep it that way. Use `yarn run check`, because bare `yarn check` is a yarn built-in.

## Architecture

**Data model (`src/lib/instruments.ts`, `parts.svelte.ts`)**: An `Instrument` (class, in `src/lib/instruments/` e.g. `Drum`, `MonoSynth`) is a stateless behaviour object; its state lives in a plain JSON-serializable `InstrumentData` containing a list of `InstrumentPartData` (identified by `partName`, which is the part class's `static id`). Each *part* (`InstrumentPart<T>` subclass: Voice, Fm, Envelope, Effects, Filter, Steps, Chords, Arpeggiator, MonoSequence, Octave, TrackNotes) declares a `stage` (where its code goes), a validator per field (`fields`, built from `field.num/bool/oneOf/steps`), `defaultData`, and `generate(data, selfData, ctx)`. Part ids and instrument `name`s are saved and sent over the network: never change them. Nothing depends on class names (no `keepNames` needed). Look parts up with `getPart(PartClass, data)` (from `parts.svelte`); all part types are listed in `PART_TYPES` (`getPartType(id)`).

**Untrusted data**: part fields end up inside Strudel code, which is evaluated as JavaScript on every peer. So the reducer validates every part with `part.normalize()` (`setPartFields`: strict, all or nothing; `addInstrument`, restore and received songs: lenient, a bad field falls back to its default, unknown parts are dropped), and `generate` clamps again. A new field needs a validator; never interpolate a string into code that is not from a fixed list.

**Code generation**: `Instrument.generate(data, scale)` is a pure function: it emits the instrument's parts sorted by `stage` (input → chords → arpeggiator, then `.fast(steps)`, then voice/FM/envelope → filter → effects: stages follow the signal), then `generateExtra` and the gain. Each part also declares a `Role` (notes, note FX, sound, sound FX: what it does to the signal, never saved). `PART_VIEWS` lists the views grouped by role in `ROLE_ORDER`, and the phone rack shows a header per role (`partViewGroups`); `components/partViews.svelte.test.ts` checks that roles, stages and views agree. Parts get a `GenContext` (loop length, scale, the input part's `degrees`, and `consumed`), never the Svelte context. Each instrument plays from its own `input` part only. A part may take over a later-stage part by adding its id to `ctx.consumed` (held chords run the arpeggiator's pattern on the chord), so dependencies between parts go one way. The song's key is song state (`store.scale`, the `setScale` command, Key/Mode in the mixer). So is its tempo (`store.tempo`, whole BPM, `setTempo`; a cycle is one 4-beat bar, `bpmToCps`; `TempoControl` in the `Transport`: nudge, slider, tap tempo from `lib/tempo.ts`). Only the host's scheduler takes it from the song (`Transport.setTempo`, which broadcasts at once); clients take the rate from the host's transport messages (`player.setCps`), so rate and position change together. Strudel's `setCps` carries the cycle position on, so a change never jumps. The whole song is a string of Strudel code evaluated by `strudel.evaluate` (`src/lib/strudel.ts`, a singleton `StrudelWrapper` around `@strudel/web`; it also polls scheduler time every 250ms into the `time` store for playhead display).

**Commands (`src/lib/commands.ts`)**: views never mutate song state. They `dispatch` a `Command` (`setCells`, `setPartFields`, `setInstrumentFields`, `addInstrument`, `removeInstrument`, `addPart`, `setLivePattern`, `setMasterVolume`, `setScale`, `setTempo`, `transport`). Commands are JSON, *absolute* (never toggle/increment), addressed by instrument `id` (never index), and anything non-deterministic (random notes, new ids) is resolved before dispatch (`lib/commandBuilders.ts`). `applySongCommand` validates and applies them in place; it also runs on network input, so it must reject anything malformed. `store.dispatch` is the single entry point: it applies locally, appends to `store.commandLog` (replayable), and sends to the host. **The host is the single sequencer**: it applies client commands and rebroadcasts them in arrival order (`ordered: true`); clients only accept the host's ordered stream, from the peer that sent them the song (`hostPeerId`; a full `'state'` from anyone else is ignored, and it goes through the reducer). That is what makes concurrent edits converge (see the randomised convergence test). Views get `dispatch` (and state) as props, so they can be tested with a spy. `lib/gesture.ts` holds the sequencer's drag rules as pure functions. Part views stay `bind:`-based (`partData = $bindable()`) against a local draft in `InstrumentPartView`, whose effect diffs it into `setPartFields`.

**Patterns (`src/lib/patterns.ts`, `cues.svelte.ts`)**: an instrument has up to 8 pattern slots (A–H). A pattern is only the notes (the input part's data); steps, chords and the sound are shared. The live slot (`livePattern`, the one the host plays for everyone) keeps its notes in `data.parts`, so generation, views and older saves see it unchanged; the others wait in `data.patterns[slot]` (null at the live slot and at slots never written). `setLivePattern` swaps them (absolute: launching the live slot is a no-op). Note edits carry a `pattern` slot (`setCells`, and `setPartFields` on the input part); a slot never written is created empty by its first edit. Views always send the slot (`patternEdit` → `withPattern` + `patternDispatch`), the live one too: "absent = live" is not absolute once launches race. What each device has open is local, never song state: `store.cues` (`PatternCues`) holds the open slot per instrument, "hear live" and launches queued for the next bar (sent `LAUNCH_LEAD_S` before the bar; at once when stopped). A non-live open slot is a *cue*: `store.localCode()` (what `+page` evaluates) plays it in place of the live notes on this device only, while `code()` stays the shared song. Devices announce their cues over an unordered `'cue'` action (validated, cleared on leave) so others see them. UI: `PatternSlots` (chips with `data-state` live/cue/queued/other/stopped/empty, from `cues.state`), `CueBanner` (hear switch, launch, "room hears" strip); hatching = not live, dashed light edge = heard here only. `PatternLauncher` is the clip-launcher grid (tracks × slots; the desktop's `patternsIndex` = -2, the phone's `patterns` screen): a column is a scene. `cues.launchColumn`/`cueColumn` act on the tracks that have notes in that slot only (the others carry on), and copying a column is client-side `setPartFields` per track (`copyPatternCommands`), not a command of its own.

**Store & networking (`src/lib/Store.svelte.ts`)**: the app talks to its own small `Room` interface (`src/lib/netRoom.ts`: `makeAction` tuples, `onPeerJoin(peerId)`), and `adaptRoom` is the only code that knows Trystero's API (0.27: `trystero` is Nostr, MQTT is `@trystero-p2p/mqtt`, picked with `?signal=mqtt`); the fake test room implements the same interface. `AppStore` (global `store`, created via `initStore(host, roomId)`; tests construct it directly with an injected room and player) holds the song as Svelte `$state` (instruments, master volume, scale), `presets` and the instrument map, and Trystero actions: `'state'` (the whole song: the host sends it when a peer connects), `'cmd'` (commands), plus `'transport'`/`'transportReq'` (`lib/transport.svelte.ts`: host-authoritative play/stop; clients mirror it, send requests, and extrapolate the playhead; sequence numbers drop stale messages). Every peer runs Strudel and plays the song itself: the host owns the transport, and clients start their scheduler at the host's position (`Transport.reconcile`: ping-compensated, output-latency-compensated, drift corrected by `shift` beyond 40 ms). Clients need a user gesture to unlock audio (`strudel.audioRunning`, the "Tap to hear" button). Compare peers' `scheduler.now()`, not wall-clock guesses; e2e measures the skew. A resync handled right after a main-thread stall (a slow phone evaluating the song) is not used for timing: a heartbeat detects the stall (`mayBeStale`). `mixerIndex = -1` addresses the mixer as a pseudo-instrument. Inside `lib/instruments/*`, import from `$lib/instruments` and `$lib/parts.svelte`, never from the `$lib` index (which pulls in the store).

**UI**: `src/routes/+page.svelte` sets the global context (`lib/context.ts`: host/roomId/scale) and renders `components/desktop/DesktopApp` (header with the transport, share and settings; `TrackList` down the side; the selected instrument or the `Mixer` in the middle) or, on phones, `components/phone/PhoneApp`. Which page shows (phone screen, selected instrument by id, desktop mixer) is in the browser's history, not component state: `lib/nav.svelte.ts` (`NavHistory`) pushes a shallow-routing entry per gesture (`pushState`, URL unchanged; changes in the same task merge into one entry) and `+page` restores `page.state.nav` on Back/Forward; the layouts get it through `bind:selectedIndex` / `bind:screen` function bindings. Leaving the jam while it plays or others are here asks first (`shouldConfirmLeave`, `beforeNavigate` in `+page`): the browser's own dialog when the page would unload (needs a prior user gesture; iOS Safari never shows it), a `confirm` for in-app links; Back/Forward between the page's own entries is never stopped. `components/InstrumentView` renders the instrument's header, its input views (`instruments/InputViewSwitcher`: grid, circles, rings, record, draw, tombola (`lib/tombola.ts`: random loops drawn from chosen rows, the balls, at a hit chance per step, the spin; written as `setCells`, on a melody the whole loop, on drums only the ball rows; "keep spinning" rolls a new loop on each loop's last step; its settings are per device. With "physics" on, `lib/tombolaPhysics.ts` simulates the drum (deterministic: fixed ticks per step, seeded PRNG, its own sin/cos) and `TombolaPlayer` plays it on this device only, each wall hit snapped to its step and scheduled ~0.12 s ahead on the song's audio clock (`strudel.songClock`, `playOnce(code, window, at)`, notes compiled ahead with `strudel.prepare`); a take records it (`Take.hitAt`), nothing else is sent; a take switches it to "Live" and back to "Loop" when it ends, so the drum never doubles the loop it recorded); the live ones record through a `Take` (`lib/take.svelte.ts`: armed for the next measure, one loop long, replaces / clears first / keeps the old notes, can loop and be undone, driven by the song clock; `instruments/TakeControls` is its card: loop strip, record button, settings sheet) and play what you hit on this device only (`lib/monitor.ts`, `strudel.playOnce`); the take card's "Loop / Live" switch (`LiveTake.heard`) picks what this device hears: on "Live" the view calls the `playHere` prop and `cues.playingHere` leaves the instrument out of `localCode()` here only, until the switch or the view closes), the `QuickControls` sliders and its rack (`RackModules`: one `InstrumentPartView` per part that has controls, in the order of `components/partViews.ts`, the part → `Part*View` registry). `Transport` (play, stop, bar.beat, key) and `Mixer` (channel strips) are shared by both layouts. Adding a part: the class (with its `stage` and `role`), its entry in `PART_TYPES`, a view in `PART_VIEWS` inside its role's group, and, if the rack may add it, the instrument's `addableParts` (`addPart` rejects anything else; drums take no voice or melody parts). Touch gestures use hammerjs via `lib/utils/hammerAction.ts`. `lib/sequencer.ts` adapts a part (steps/notes) to the grid `ISequencer` interface.

**Phone layout and look**: below Tailwind's `md` breakpoint `+page` renders `components/phone/PhoneApp` instead of the desktop layout (`lib/utils/media.svelte.ts`; without `matchMedia`, as in jsdom, it is the desktop one). Four screens behind a bottom tab bar: Session (`SessionView`: transport, one card per track with a mini pattern, mute/solo), Edit (input view + `QuickRack`, a strip of knobs), Rack (`RackModules` stacked, with a header per role) and Mixer (`Mixer` + `SettingsPanel`). Only one screen shows at a time, so there is exactly one Play button on screen. The look is the `taliesin` Skeleton theme (`src/theme/taliesin.css`, dark). Each instrument's colour (`lib/trackColors.ts`) comes from its index, not from song state; the Edit/Rack screens and the desktop's `InstrumentView` set it as `--color-primary-500` so the grid and sliders wear it. Desktop and phone share `Transport`, `Mixer`, `RackModules` (desktop: `layout="grid"`, one grid in signal order, each module captioned with its role), `InstrumentMenu`, `SettingsPanel` and `ShareButton`. `RackModules` sets the `rack` control style (`lib/controlStyle.ts`, a context): the same `Param*` controls then draw as knobs (`Knob`, maths in `lib/knob.ts`), chips, compact steppers, and an `enabled` toggle marked `power` moves into the module header; part views stay unchanged. Grid cells carry `cell-on`/`cell-off`/`cell-preview`/`cell-erasing` and the playhead `data-now`, which tests read instead of colour classes.

**Start page & saving**: `/home` starts a jam (`lib/room.ts`: short room codes, `parseRoom` accepts a pasted share link or code). The host autosaves the song to `localStorage` per room (`taliesin:song:<room>`, debounced, restored through the command reducer so bad data is dropped); clients never save.

**Acoustic calibration (`src/lib/calibration/`)**: the browser's reported output latency is often wrong (Bluetooth), so devices in the same room can be measured. The host's "Calibrate" button records its microphone while each guest plays a probe chirp on request; the host times the arrival against its own speaker-to-mic delay (same input path, so mic latency cancels) and sends the guest `round`; the guest subtracts the network delay it assumes and applies the result as `transport.offset`, which *replaces* the reported-latency term in `Transport.target()`. `dsp.ts` is pure (chirps, FFT, normalised cross-correlation: raw correlation peaks accept any loud beep, so keep it normalised); `calibration.svelte.ts` is the protocol over an injected `Acoustics`; `webAcoustics.ts` is the real Web Audio/AudioWorklet implementation. Unit tests simulate the air; e2e loops the real audio graph back into the worklet. Only meaningful for co-located devices, with the song stopped.

**TURN relay (`src/lib/turn.ts`, `worker/`)**: peers on mobile data or strict NATs need a TURN relay. `routes/+page.ts` fetches short-lived ICE servers from `VITE_TURN_ENDPOINT` (or `?turn=<url>`) before the room is joined; failure just means no relay. `worker/turn.ts` is the Cloudflare Worker that holds the API token (setup in `worker/README.md`). Static `VITE_TURN_URLS/USERNAME/CREDENTIAL` also work for providers with fixed credentials.

**Connectivity problems**: see `docs/connectivity.md` (what fixed phone-to-PC connections, the secure-context and clock-skew traps, and how to read the `?debug` panel).
